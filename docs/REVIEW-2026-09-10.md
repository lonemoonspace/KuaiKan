## 1. 性能与体积（建议优先处理）

### 1.1 content script 688 KB，注入每一个页面 —— 这是最大的一笔成本

**位置**：`entrypoints/content/index.ts:6`（`matches: ['<all_urls>']`）
/ `.output/chrome-mv3/content-scripts/content.js`（704,108 字节）

每打开一个网页，浏览器都要下载（本地）+ **解析**这 688 KB，无论用户是否打算总结这一页。
包里含 React 19、AI SDK UI 层、sonner、Radix、marked。

更关键的一点：**构建产物里没有 content 的 chunk**（`.output/chrome-mv3/chunks/` 只有
options / popup / style 三个）。也就是说 `message.tsx:70` 里那个 `import('marked')` 被
**内联进了同一个文件** —— 它延后的只是**执行**，不是下载和解析。AGENTS.md 技术栈表里写的
"marked（动态导入）"容易让人误以为拿到了体积收益，实际没有。

站点黑白名单也救不了：`scope.tsx:62-70` 只是决定**要不要挂载 UI**，bundle 本身照样加载解析。

**改法（按投入从低到高）**：

1. 最省事：把面板 UI 从静态 content script 里拿掉，content script 只留一个几 KB 的"探针"
   （挂悬浮球 + 响应 `ping`/`extractText`），真正的 React 面板用
   `browser.scripting.executeScript` 或动态 `import()` 在用户第一次打开面板时才注入。
2. 或者：面板改成 `chrome-extension://` 的 iframe，content script 只负责定位和消息转发。
   代价是拖拽/缩放要跨 iframe 协调，且失去与页面同 DOM 的便利（`window.find` 溯源会受影响）。
3. 最低成本的部分收益：确认 WXT/Vite 的 content script code splitting 配置，至少让 marked
   真的落到独立 chunk。

### 1.2 background.js 2.58 MB 单文件，每次冷启动都要全量解析

**位置**：`.output/chrome-mv3/background.js`（2,710,695 字节）

同样的内联问题：`token-count-bg.ts:21` 的 `import('gpt-tokenizer/model/gpt-5')` 也被内联进了
`background.js`。MV3 service worker 空闲约 30 秒就被终止，**每次唤醒都要重新解析这 2.58 MB**。
这直接体现为"点了总结之后要等一下才开始"。

体积主要来自 gpt-tokenizer 的 BPE 表 + 六个 provider SDK。Provider SDK 那部分可以按
`config.providerId` 动态 import（`lib/model-provider.ts:23-54` 的 switch 天然适合改成
`await import()`），但同样要先确认 background 的 code splitting 是否生效 —— 如果不生效，
改造是白做的。**建议先花十分钟验证 chunk 能不能产出，再决定要不要动。**

### 1.3 dom-heuristic 模式每次都白跑一遍完整 Readability

**位置**：`lib/page-extraction.ts:371-373`

```ts
export function domHeuristicParseRead(sourceDocument: Document = document) {
  const readabilityArticle = getReadabilityArticle(sourceDocument);   // 克隆整个 document + 完整解析
  const readabilityTextLength = readabilityArticle?.textContent
    ? cleanExtractedText(readabilityArticle.textContent).length
    : undefined;
```

`getReadabilityArticle` 会 `cloneNode(true)` 整个文档再跑 Readability —— 全流程最贵的一步 ——
而它的产物在 dom-heuristic 分支里**只被用来算一个 `readabilityTextLength` 数字**，正文一个字
都没用上。这个字段在 `WebpageContent` 里是可选的，翻遍代码只在类型定义里出现。

**改法**：删掉 `readabilityTextLength`，或者把它变成"仅在 debug 日志级别下计算"。

### 1.4 `innerText` 在候选筛选里被反复调用，每次强制 layout

**位置**：`lib/page-extraction.ts:171-174`（`getElementText`）、`185-199`（`isCandidateElement`）、
`241-262`（`getCandidateMetrics`）

`getElementText` 用 `innerText`，这会**强制同步 layout**。而它被调用的地方是：

- `isCandidateElement` —— TreeWalker 遍历 body 下**每一个** `ARTICLE/MAIN/SECTION/DIV`
- `getCandidateMetrics` —— 每个候选元素一次，**外加该元素内每一个 `<a>` 一次**（`254-257` 的 reduce）

在链接密集的大页面（论坛、聚合站）上，这轻松是几千次 forced reflow，且没有任何缓存。
同一个元素在筛选阶段和评分阶段各算一遍。

**改法**：加一个 `WeakMap<Element, string>` 缓存 `getElementText` 的结果（单次提取内有效即可），
或者在筛选阶段改用 `textContent`（不触发 layout，长度足够做粗筛），只在最终评分用 `innerText`。
前者改动小、收益直接。

### 1.5 `behaviour === 'nothing'` 时白编码一次全文，且有一段死代码

**位置**：`entrypoints/background/token-count-bg.ts:63-71` 与 `39-42`

```ts
const tokenizer = await loadTokenizer();
const tokens = tokenizer.encode(text);          // ← 先编码
...
if (originalTokens <= maxTokens || behaviour === 'nothing') {
  return text;                                   // ← 再发现根本用不上
}
```

`behaviour === 'nothing'` 的分支应该在 `encode` **之前**早退。附带后果：
`applyTruncationStrategy` 里的 `if (behaviour === 'nothing') return tokenizer.decode(tokens)`
（39-42 行）**永远不可达** —— 两个调用点都在进入它之前就把 `'nothing'` 拦掉了。这段是死代码。

## 2. 正确性与健壮性

### 2.1 站点黑白名单在已打开的标签页里不会生效，直到刷新

**位置**：`entrypoints/content/scope.tsx:62-68`

```ts
let urlAllowed = true;
try {
  const { whitelist, blacklist } = await loadSiteRules();
  urlAllowed = isUrlAllowed(location, whitelist, blacklist);
} catch (e) { ... }
```

`urlAllowed` 只在挂载时求值一次，随后被 `ping`（80-87）和 `extractText`（89-123）的闭包捕获。
用户在设置页把某站加进黑名单后，**已经打开的那些标签页**照旧响应 `extractText`、popup 也照旧
显示"此页面可总结"。

自用场景下影响有限，但这是一个"设置改了没反应"的典型困惑源。要么加 `storage.watch` 重新求值
（几行），要么在设置页的说明里写清"需要刷新页面生效"。

### 2.2 导入配置会把本地 API Key 带到传入配置指定的端点

**位置**：`entrypoints/options/pages/ConfigManagerPage.tsx:53-87`（`mergeModelSecrets`）
+ `201-221`

`mergeModelSecrets` 的设计意图是好的（默认导出不含密钥，导入时不要清空用户的 key，
这是 1.6.0 修的一个真 bug）。但合并的匹配键**只有 `id`**：

```ts
const local = typeof incoming.id === 'string' ? localById.get(incoming.id) : undefined;
if (!local) return item;
...
if (!merged.apiKey && local.apiKey) merged.apiKey = local.apiKey;
```

一份"id 相同、`baseURL` 指向别处"的配置文件，导入后就会拿着你的 key 去打别人的端点。
`importSchema` 的 `data: z.record(z.string(), z.any())` 对值不做任何校验，所以文件里可以塞任何东西。

缓解因素：导入有 diff 审阅界面，`newValue` 会完整显示出来，用户理论上能看见 baseURL 变了。
且这是自用扩展，导入的通常是自己导出的文件。

**建议**（成本很低）：在 `mergeModelSecrets` 里加一条 —— `incoming.baseURL` 与 `local.baseURL`
不同时，**不继承** apiKey / headers。一行判断，把这个面彻底关掉。

### 2.3 无法识别的 provider 会被静默丢弃，用户得不到任何提示

**位置**：`lib/model-settings-storage.ts:71-121`

`parseModels` → `filter(isModelConfigItem)` → `isModelProviderId(model.providerId)`。
一条 `providerId` 不在 `MODEL_PROVIDER_DEFINITIONS` 里的记录会被**无声过滤掉**，
模型列表里就此消失，没有 toast、没有日志。

现实触发路径：老版本存过的 `browser-ai` 模型（该 provider 已在 2.0.0 移除，见 §3.1）。
用户升级后打开设置页，只会看到模型少了一个。

**建议**：至少在 `parseModels` 里对被丢弃的行 `logger.warn` 一条，带上 `providerId` 和 `name`。

## 4. 重复与整洁

### 4.1 token-count 的类型和常量存在两份完全相同的定义

**位置**：`lib/token-count.ts` 与 `entrypoints/background/token-count-bg.ts`

两个文件各自声明了：

- `export const INPUT_TOKEN_COUNT_MODEL = 'gpt-5'`
- `InputTokenCountTiming` / `InputTokenCountResult` / `TruncateByTokensResult`
  / `TokenPiece` / `SplitTokensResult`

而 `lib/messaging.ts:16-19` 的 `ProtocolMap` 引用的是 **`lib/token-count.ts`** 那一份：

```ts
countInputTokensWithTiming(input: { text: string }): import('./token-count').InputTokenCountResult;
```

也就是说 background 的实现返回的是 `token-count-bg.ts` 的类型，协议声明的是 `token-count.ts` 的类型，
两者靠**结构相同**才对得上。改一边不改另一边，只要字段没冲突，**编译器不会报错**，
错误会一路漏到运行时。

**改法**：把常量和 5 个类型收进一个共享文件（`constants/token-count.ts` 更符合本项目
"常量集中在 constants/" 的约定），两侧都从那里 import。纯移动，无行为变化。

import { createLogger } from '@/lib/logger';

## 5. 测试与工程配置

### 5.1 `npm run compile` 不检查测试代码

**位置**：`tsconfig.json` 的 `include` 数组

`include` 列了 components / constants / entrypoints / hooks / lib，**没有 `test/**`**，
也没有 `vitest.config.ts`。测试文件里的类型错误只有在 `vitest run` 真跑到那一行时才会暴露，
而 tsgo 全程沉默。加两行就能修。

### 5.2 测试覆盖集中在纯函数，核心时序路径无覆盖

当前 65 个用例的分布：

| 文件 | 用例 | 覆盖对象 |
|---|---|---|
| `test/components/message.test.ts` | 13 | citation 抽取/回填、HTML 转义 |
| `test/lib/error-taxonomy.test.ts` | 13 | 错误分类（status 优先、abort 整词） |
| `test/lib/migration.test.ts` | 12 | `local:` 前缀不变量、幂等性 |
| `test/lib/site-rules-storage.test.ts` | 12 | glob 匹配、白/黑名单优先级 |
| `test/lib/page-extraction.test.ts` | 9 | 正文清洗 |
| `test/background/token-count-bg.test.ts` | 6 | 四种截断策略 |

选得很准 —— 这几处都对应 CHANGELOG 里真出过事的地方。但**完全没有覆盖的恰恰也是出事最多的两类**：

1. **connect bridge 的帧协议**（`entrypoints/background/ai-sdk-connect-bridge.ts`）。
   `streamMessages` 里有一堆微妙的状态交互：`streamFailed` 标志、`onError` 与外层 catch 的
   去重、"零 chunk 也要报错"、abort 后忽略错误。`postErrorFrame` / `getErrorMessage`
   （解析 provider JSON 错误体、跳过 HTML 错误页、截断到 300 字符）一个分支都没测。
   这些是纯函数或近乎纯函数，**很好测**。
2. **`useContentApp` 的初始化与自动总结时序**。1.5.1 的 stale-closure 事故就发生在这里，
   代码里那段 13 行的注释本质上是在用文字代替测试。加 `@testing-library/react` 是一笔
   新依赖（`SIMPLIFY_PLAN.md` 明确说"不引入新的运行时依赖"，但 devDependency 不在此列），
   要不要付这笔成本由你判断。

**如果只做一件事**：给 bridge 的 `getErrorMessage` 补一组用例（JSON 错误体 / HTML 错误体 /
无 body / 无 status 四种输入），成本 20 分钟，直接守住一条历史上炸过的路径。

### 5.3 ESLint 可以低成本多抓一类问题

**位置**：`eslint.config.js`

只开了 `react-hooks/rules-of-hooks` 和 `react-hooks/exhaustive-deps` —— 这个选择是有道理的
（配置里的注释说明了理由，`exhaustive-deps` 确实是这个项目被咬过的规则）。

但加一条 `@typescript-eslint/no-unused-vars`（`typescript-eslint` 已经是 devDependency）
就能自动抓到 §4.2 那类死代码，且几乎不会产生噪音。建议以 `warn` 级别加上。

### 5.4 `docs/SIMPLIFY_PLAN.md` 是一份已执行完的计划

479 行的 2.0.0 重构计划，工作已经完成并写进 CHANGELOG。CHANGELOG 2.0.0 #12 里提到当时
